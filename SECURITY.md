# Security

## Scope and support

This experimental plugin is currently maintained at source version `0.2.0`. Fixes target the latest source revision; older snapshots have no backport commitment. Maintainer response times are best effort, with no promised service level.

Tern plugins are trusted local code. Inspect source before installing. Tern Tab Status uses host pane enumeration, window pane/surface metadata, local CSS, tabs, timers, events, commands, settings, actions and key/value APIs. The host publishes full native pane ID strings; the window identifies supported executables and targets native `data-pane`/`data-st` elements. Production does not call `agents:list()` or request its assistant-text field. Shell-hosted OMP identification reads at most one surface node, depth one and 128 characters to identify the `omp.session` role; returned content is not persisted. Explicit **New OMP Tab** and **New Pi Tab** commands start `omp` or `pi` without an initial prompt, temporarily selecting and then restoring the Agent command and placement, including on creation errors. The plugin makes no network requests, installs no agent hooks and stores no conversation text.

Saved plugin state includes enabled/paused status, native pane IDs and per-pane read markers. Markers record whether a result was viewed, not its content. Status CSS leaves native manual `tab.color` unchanged. Older original/applied color records are used only for upgrade restoration: write the old original only while current color equals old applied, retain the record if readback does not show success, and preserve a different current manual color. Large-ID SDK failures can leave those old records unresolved. Tern owns storage under `plugin-data/tern-tab-status/kv.json`; unlinking does not erase it. Pause before removal to hide status styling and retry legacy restoration. Do not publish storage files: they contain local pane/session identifiers.

The plugin has no production dependencies. The pinned development-only Luau runtime is installed through npm for checks. npm installation contacts the configured registry; plugin execution does not.

The separate development runner, `node scripts/verify-native.mjs`, starts real agents with a test-only offline provider in its own Tern configuration and daemon. Its observer may read complete agent metadata; it is never installed in the daily configuration. The runner retains native metadata, screenshots, pixel-derived `statusColor`, logs, source hashes and process receipts at the printed evidence directory. Native `tab.color` is an independent manual-color check. Artifacts are local verification output, not plugin runtime storage. Review them before sharing; do not publish daily-session captures or raw conversation data. Automated confirmation dialogs require no user action, are observed for five seconds and are closed with Escape. The [verification skill](./.cursor/skills/verify-tern-tab-status/SKILL.md) defines isolation and cleanup.

## Reporting privately

Use [GitHub's private vulnerability reporting form](https://github.com/yoyooyooo/tern-tab-status/security/advisories/new). Private reporting is enabled for this public repository. Do not post credentials, full conversation logs, or plugin storage in a public issue.

Include the plugin and Tern versions, OS/architecture, expected and observed behavior, impact, and the smallest reproduction that avoids private session data. Reports are handled on a best-effort basis as described above.

## Limit of the indicator

Status dots are attention hints. Green does not verify task success, and absence of a dot does not prove no agent is running: recognition, native markup and current read/pause state must cooperate. The plugin never acknowledges native attention. Exact native pane CSS avoids the SDK color bridge for status display. The copied-source run, selected daily lookup/display and 12 controlled high-ID lifecycle observations provide bounded evidence; the SDK limitation still affects restoration of old color records. Tern's timer-budget mechanism remains unresolved. Native states drive installed CSS without production agent-list polling, and lifecycle events synchronize recognition/styles directly without waiting for a timer. Stopped timers can still delay changes without a delivered event, including cross-window pause in a quiet window. OMP standalone extension confirmation dialogs can remain native `idle` and produce no yellow dot. See the [current evidence](./docs/readiness.md#current-css-cutover-evidence) and [known native blockers](./docs/readiness.md#known-native-blockers); do not use the indicator as an approval or security boundary.
